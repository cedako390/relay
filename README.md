# Orchestrator

Локальная веб-панель для управления несколькими сессиями Claude Code. Бэкенд запускает обычный
интерактивный `claude` в псевдотерминалах (PTY, на Windows через ConPTY), фронт показывает сессии,
задачи и живой терминал. Агенты общаются с бэкендом через MCP и хуки. Проект личный: один
пользователь, только `127.0.0.1`.

* Авторизация идёт через подписку Claude. API-ключи и Agent SDK не используются; `ANTHROPIC_API_KEY`
  (и `ANTHROPIC_AUTH_TOKEN`) удаляются из окружения каждого дочернего `claude`.
* Нет Docker, Tauri и tmux. Electron есть только как оболочка окна (`packages/desktop`), логики в нём нет.

## Требования

* Node.js ≥ 22 (проверено на 24), pnpm ≥ 10 (проверено на 12), установленный и залогиненный `claude` в `PATH`.
* `node-pty` и `better-sqlite3` ставятся из prebuilds, компилятор не нужен. pnpm по умолчанию блокирует
  build-скрипты зависимостей; разрешены они в `pnpm-workspace.yaml` (`allowBuilds`).
  Если prebuild для вашей платформы не нашёлся, понадобятся build tools (Windows: Visual Studio Build
  Tools + Python; Linux: `build-essential python3`; macOS: Xcode CLT).

## Запуск

```sh
pnpm install
pnpm dev          # сервер (127.0.0.1:4180) + web (127.0.0.1:5173) параллельно
```

Откройте `http://127.0.0.1:5173/`. Входа и токена нет: сервер рассчитан на запуск только на своём ПК.

Продакшен-режим (одна origin, сервер раздаёт собранный фронт):

```sh
pnpm build
pnpm --filter @orch/server start   # http://127.0.0.1:4180/
```

Скрипты в корне: `pnpm dev | build | typecheck | test | db:generate | db:migrate`.
Миграции применяются автоматически при старте сервера; `db:migrate` нужен только для ручного запуска,
`db:generate` создаёт новую миграцию после правки `packages/server/src/db/schema.ts`.

## Где что лежит

| Путь | Что |
|---|---|
| `data/orchestrator.db` | SQLite (WAL, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=NORMAL`); пишет только процесс сервера |
| `data/sessions/<id>/` | `settings.json` (хуки) и `mcp.json` для конкретной сессии |
| `data/worktrees/<task-id>/` | git worktree воркера (ветка `orch/<task-id>`) |
| `data/workspace/` | рабочая папка по умолчанию для задач без `cwd` |
| `.env` | конфиг (см. `.env.example`), валидируется zod при старте |

`data/` и `.env` в `.gitignore`.

## Как это работает

* **Сессии.** `POST /api/sessions {cwd, model?, taskId?}` запускает `claude --settings <hooks> --mcp-config <mcp> [--model X]`
  в PTY. Процесс живёт в памяти сервера, состояние в БД. Закрытие вкладки терминал не убивает;
  при подключении `/ws/terminal/:id` сервер отдаёт кольцевой буфер последних ~256 КБ вывода.
  Выход с кодом 0 или `DELETE /api/sessions/:id` даёт `closed`, иначе `dead`.
* **Хуки.** Конфиг передаётся флагом `--settings`, поэтому ни глобальные настройки, ни `.claude/` проекта не
  меняются. Каждый хук запускает `packages/server/scripts/hook.mjs`, который шлёт stdin-JSON на `/api/hooks`.
  Машина состояний (`sessions/status.ts`): `SessionStart`/`Stop` → `idle`; `UserPromptSubmit`/`PreToolUse`/
  `PostToolUse`/`PreCompact` → `busy`; `Notification`/`PermissionRequest` → `waiting`; `SessionEnd` → `closed`;
  `SubagentStart/Stop` считают `active_subagents`. Все события пишутся в таблицу `events`.
* **Сверка по заголовку окна.** Хуки не видят прерывание по Esc и ответ на запрос разрешения, поэтому раз в секунду
  статус сверяется с заголовком окна `claude` (`✳` ждёт ввода, `◐◑` работает): `waiting → busy` после выдачи
  разрешения, `busy → idle` после Esc (около 5 с). Каждая поправка пишется событием `OrchReconcile`.
* **Страховка.** Раз в 5 с проверяется, жив ли процесс. `busy` без активности дольше 10 минут помечается
  флагом `suspicious` (⚠ в UI), статус при этом не меняется.
* **Очередь сообщений.** `POST /api/sessions/:id/messages` кладёт сообщение в `messages`. Доставка только
  при `idle`: bracketed paste (`ESC[200~ … ESC[201~`), через 250 мс отдельный `Enter`.
* **Задачи и воркеры.** `create_task` создаёт задачу и запускает воркера в новой сессии (если cwd это git-репозиторий,
  то в отдельном worktree). Первый промпт воркер получает через ту же очередь. После `report_result` и
  следующего `Stop` воркер закрывается автоматически, чтобы освободить слот. Выход сессии без отчёта: `done`
  (код 0), `failed` (процесс умер), `cancelled` (завершили вручную).
* **Уведомление о результате.** Когда задача завершается (`done`/`failed`/`cancelled`), сессии, которая её создала,
  в очередь кладётся сообщение `[Orchestrator] Task "…" finished with status: …` с результатом (если сессия ещё жива).
  Опрашивать `get_task` не нужно.
* **Встроенные субагенты отключены.** По умолчанию (`BLOCK_NATIVE_SUBAGENTS=true`) в сессиях из панели запрещён
  встроенный инструмент `Agent` (`--disallowedTools`) и в системный промпт добавлена инструкция делегировать
  через `create_task`. Иначе модель на «создай субагента» запускает невидимого для системы нативного
  субагента (без задачи, сессии и терминала). Отключается `BLOCK_NATIVE_SUBAGENTS=false`.
* **Лимиты.** `MAX_WORKERS` (4): лишние задачи остаются `queued` и стартуют по мере освобождения слотов.
  `MAX_DEPTH` (3): глубина дерева задач, корневая задача имеет глубину 1. Модели из `ALLOWED_MODELS`, иное
  заменяется на `DEFAULT_MODEL`.
* **Вложенные оркестраторы.** Оркестратор (не воркер) может запустить другого инструментом `create_orchestrator`, например
  отдельно на фронт и на бэк из большого TODO.md; каждый раздаёт своей части воркеров через `create_task`. Новый
  оркестратор получает задание первым сообщением и по окончании сам шлёт отчёт родителю (`send_message`); родитель закрывает
  его через `close_session`. Лимиты: `MAX_SUB_ORCHESTRATORS` (4 активных одновременно, `0` отключает) и
  `MAX_ORCHESTRATOR_DEPTH` (2: сессия пользователя имеет глубину 1). Воркеры всех оркестраторов делят общий `MAX_WORKERS`.
* **Безопасность.** Слушаем только `127.0.0.1`; проверяются `Host` (защита от DNS rebinding) и `Origin`
  (если он есть, то из `ALLOWED_ORIGINS`; закрывает доступ с чужих сайтов, включая WebSocket). Входа по токену нет.

## Подключение MCP к Claude Code

Сессии, запущенные из панели, получают MCP-сервер автоматически (через `--mcp-config`, заголовок
`X-Orch-Session` подставляется из окружения процесса). Чтобы подключить его к «внешнему»
`claude`, запущенному в обычном терминале:

```sh
claude mcp add --transport http orchestrator http://127.0.0.1:4180/mcp
```

Такой клиент не передаёт `X-Orch-Session`, поэтому `create_task` работает, но без родительской задачи и cwd
по умолчанию, а `report_result` отклоняется (нужна сессия, запущенная панелью).

Инструменты: `create_task(title, description, model?, parent_id?)`, `get_task(id)`, `list_children(parent_id)`,
`report_result(task_id, status, result)`, `send_message(session_id, body)`, `create_orchestrator(title, instructions, cwd?, model?)`,
`close_session(session_id)`.
Личность вызывающего определяется заголовком `X-Orch-Session`, а не аргументами модели.

## Ограничения и известные особенности

* **Диалог доверия папке.** Первый запуск `claude` в новой папке показывает «Do you trust this folder?»
  (по умолчанию выбрано «No, exit»). Подпапки уже доверенной папки доверие наследуют, но **git worktree
  считается отдельным проектом**, и воркер в нём будет ждать подтверждения (статус `starting`) прямо в
  терминале. Варианты: подтверждать вручную в UI или включить `AUTO_TRUST_WORKTREES=true`: тогда сервер сам
  отвечает «Yes», только для папок внутри `data/worktrees`, которые создал сам. Claude при этом сам запишет
  доверие в свой `~/.claude.json`. По умолчанию выключено.
* **Запросы разрешений.** Если режим разрешений `claude` требует подтверждений, воркер встанет в `waiting`;
  отвечать нужно в терминале. Для автономной работы настройте разрешения в своём `claude` или задайте
  `CLAUDE_PERMISSION_MODE`.
* **Notification `idle_prompt`** приходит через ~60 с после ответа и *не* переводит сессию в `waiting`
  (иначе очередь сообщений зависала бы). В `waiting` переводят `permission_prompt` и `PermissionRequest`.
* **Готовность ввода.** `SessionStart` приходит раньше, чем TUI готов принимать текст. Поэтому очередь ждёт, пока
  в потоке PTY появится баннер «Claude Code v…» и стабильно включится bracketed paste (запасной таймаут 15 с).
  Если Anthropic изменит баннер, доставка первого сообщения задержится до таймаута.
* Перезапуск сервера завершает все сессии (дочерние процессы умирают вместе с ним), а запись в БД
  помечается `dead`. Возобновления (`--resume`) нет.
* Worktrees и ветки `orch/*` после завершения задач не удаляются, чтобы результат работы не пропал.
* Поддерживается один пользователь и один экземпляр сервера на `DATA_DIR`.
* Тесты: vitest на машину состояний, очередь, лимиты, задачи, watchdog. Всё остальное проверялось запуском.

## Десктоп-приложение (Electron)

Окно вместо браузера: `packages/desktop` поднимает сервер (если он ещё не запущен) и открывает его в окне.
В полях «Working directory» появляется кнопка «Выбрать…» с системным диалогом выбора папки.

```sh
pnpm app          # pnpm build + запуск окна
pnpm app:quick    # только окно, если уже собрано
pnpm app:dev      # разработка: окно само подхватывает правки
```

`pnpm app:dev` ничего не требует собирать заранее. Фронт идёт через Vite с HMR (правки видны в окне сразу),
сервер и `@orch/shared` пересобираются esbuild в `packages/server/dist`, и после каждой успешной сборки сервер штатно
останавливается и запускается заново. Правки main/preload Electron перезапускают окно. Если сборка упала, продолжает
работать прошлая версия. Закрытие окна или Ctrl+C гасит всё. Это отдельный экземпляр (сервер `127.0.0.1:4185`, Vite
`5183`, `DATA_DIR=./data/dev`, свой профиль Electron), поэтому рабочее окно и его сессии не трогаются. Порты и папку
можно поменять через `ORCH_DEV_PORT`, `ORCH_DEV_VITE_PORT`, `ORCH_DEV_DATA_DIR`. Перезапуск сервера убивает сессии
dev-экземпляра (их можно поднять через resume). Типы не проверяются, для этого `pnpm typecheck`.

Двойной клик по `Orchestrator.vbs` запускает окно без консоли (нужен предварительный `pnpm build`).
Сервер запускается системным `node` (нативные модули собраны под Node, не под Electron) и останавливается
при закрытии окна. Если сервер уже работает на этом порту, окно просто подключается к нему и не трогает его.
Порт берётся из `PORT`/`.env`. В обычном браузере всё работает как раньше, но без кнопки выбора папки.
