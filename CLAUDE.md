# Orchestrator: заметки для разработки

Личная локальная панель для управления несколькими сессиями Claude Code. Бэкенд запускает обычный
интерактивный `claude` в PTY (Windows: ConPTY), фронт показывает сессии, задачи и живой терминал, агенты
говорят с бэкендом через MCP и хуки. Бэкенд единственный источник правды. Запуск и конфиг: `README.md`.
Если этот файл расходится с кодом, прав код.

## Жёсткие правила проекта
- Без Docker/Tauri/tmux, без API-ключей и `@anthropic-ai/claude-agent-sdk`. Только CLI `claude` на подписке.
  У дочерних процессов вырезаются `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` и маркеры родительской сессии
  Claude Code (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, …), см. `sessions/pty.ts`.
- Сервер слушает только `127.0.0.1`; входа по токену нет (запуск только на своём ПК). Защита: у всех запросов
  проверяется `Host` (DNS rebinding), у `/api`, `/mcp`, `/ws` ещё `Origin`, если он есть (иначе чужой сайт
  откроет WebSocket и получит терминал). Это единственный барьер, не ослаблять. Запросы не логируются (шум).
- Пути только через `node:path`. TypeScript strict, ESM, без `any`. Сервер не импортирует `electron`
  (в будущем его можно будет завернуть).
- В БД пишет только процесс сервера, одно соединение. PRAGMA: WAL, busy_timeout=5000, foreign_keys=ON, synchronous=NORMAL.
- Сортировка «по порядку создания» делается по `rowid`, не по `id` (UUID случайные, `created_at` в мс совпадает).

## Структура
`packages/shared` (zod-схемы, исходники без сборки), `packages/server` (`config db sessions hooks queue mcp tasks auth
events routes`, composition root в `context.ts`), `packages/web` (React, Zustand держит живое состояние, TanStack
Query только грузит снимок). Ключевые файлы: `sessions/status.ts` (чистая машина состояний), `sessions/manager.ts`
(PTY и жизненный цикл), `sessions/live-session.ts` (буфер вывода, детекторы), `queue/service.ts` (доставка),
`tasks/service.ts` (лимиты, воркеры, уведомления), `mcp/tools.ts`, `scripts/hook.mjs`.

## Как устроено (проверено на `claude` 2.1.296, Windows 10, Node 24, pnpm 12)
- **Конфиг на сессию** передаётся флагами `--settings data/sessions/<id>/settings.json` (хуки, exec-форма
  `node hook.mjs`) и `--mcp-config .../mcp.json` (заголовок
  `X-Orch-Session: ${ORCH_SESSION_ID}` раскрывается из окружения процесса). Репозиторий и глобальные настройки не трогаются.
- **Статусы:** SessionStart/Stop → idle; UserPromptSubmit/PreToolUse/PostToolUse/PreCompact → busy;
  PermissionRequest и Notification кроме `idle_prompt`/`auth_success` → waiting; SessionEnd → closed;
  Subagent* считают счётчик. `idle_prompt` приходит через ~60 с простоя и игнорируется (иначе очередь встанет).
- **Очередь сообщений:** доставка только при `idle`: bracketed paste, через 250 мс отдельный `\r`. Сразу после
  вставки сессия оптимистично ставится в `busy`. Многострочный текст с пустыми строками и спецсимволами дошёл целиком.
- **Готовность ввода (грабли):** SessionStart приходит раньше, чем TUI принимает текст; вставка в это окно
  печатается как обычный вывод и теряется. Очередь ждёт баннер «Claude Code v…» (после очистки ANSI) и 500 мс
  стабильного `ESC[?2004h`; запасной таймаут 15 с.
- **Диалог доверия папке:** подпапки доверенной папки наследуют доверие, **git worktree нет** (отдельный проект).
  `AUTO_TRUST_WORKTREES=true` отвечает «Yes» только в `data/worktrees/*` (по умолчанию выключено).
- **Скролл терминала:** `claude` 2.1.x по умолчанию может рисовать в «fullscreen»-режиме (перерисовка окна с `ESC[H`, историю держит
  само приложение), тогда в xterm нет scrollback и колесо ничего не листает. `buildChildEnv` ставит `CLAUDE_CODE_NO_FLICKER=0`
  (классический рендерер, строки уходят в scrollback). Проверено на живом `claude`: 120 строк, история листается. Свою `CLAUDE_CODE_NO_FLICKER` в окружении сервера уважаем.
- **Субагенты:** по умолчанию (`BLOCK_NATIVE_SUBAGENTS`) встроенный `Agent` запрещён и добавлена инструкция
  использовать `create_task`; иначе на «создай субагента» модель запускает нативного, невидимого для системы.
- **Задачи:** воркер получает промпт через очередь; после `report_result` и следующего Stop закрывается сам;
  создателю задачи (`tasks.creator_session_id`) в очередь кладётся сообщение с итогом, опрашивать не нужно.
  Сессия закончилась без отчёта: closed → done, dead → failed, убита вручную → cancelled.
- **Вложенные оркестраторы:** MCP `create_orchestrator` (`sessions/sub-orchestrators.ts`) запускает обычную сессию `kind=orchestrator`
  с `sessions.parent_session_id`; задание уходит первым сообщением через очередь. Вызывать может только оркестратор (воркер получает 403).
  Лимиты: `MAX_SUB_ORCHESTRATORS` активных (считаются все сессии с родителем, `0` выключает) и `MAX_ORCHESTRATOR_DEPTH`
  (сессия пользователя = 1). Отчёт родителю ребёнок шлёт сам через `send_message`; если ребёнок умер/закрылся сам, сервер кладёт
  родителю уведомление (при `close_session` нет). `close_session` закрывает только своих детей; их воркеры доживают сами.
  Воркеры вложенных оркестраторов делят общий `MAX_WORKERS`, поэтому слоты воркеров на оркестраторов не тратятся (у них свой счёт).
  Проверено запуском: MCP-вызовы, лимиты, запись родителя в БД (второй экземпляр, `CLAUDE_BIN=node`); с настоящим `claude` не гонялось.
- **Терминал вместо «session closed»:** если `claude` вышел сам (двойной Ctrl+C, `/exit`, падение), `SessionManager.continueInShell`
  запускает `SHELL_BIN` (Windows: `powershell.exe`) в том же `LiveSession`: тот же сокет и вкладка, история экрана остаётся,
  зрители не получают `exit`. Сессия получает статус `shell` (активный; хуки и сообщения для неё игнорируются/отклоняются,
  `canReceiveMessages`), пид меняется, `claude_session_id` остаётся. Выход из шелла даёт `closed`, дальше клик по вкладке делает
  `claude --resume`. Не для воркеров и вложенных оркестраторов, и не при `kill` (Terminate, остановка сервера). Поздний
  `SessionEnd` от старого `claude` на `shell` не действует (`status.ts`). Чтобы переход был без паузы: `SessionEnd` приходит
  раньше выхода процесса, поэтому для таких сессий он не ставит `closed` (иначе вкладка показывает «Session closed», пока
  `claude` дозавершается), а `SessionManager.handleSessionEnd` сразу запускает шелл в фоне (`warm`), копит его вывод и отдаёт
  терминалу в момент выхода `claude`. `reason: clear` (`/clear`) шелл не запускает. Фоновый шелл гасится при `kill`, `finish`,
  остановке сервера и через 30 с, если `claude` так и не вышел.
- **Терминальные сессии:** `POST /api/sessions {kind:'terminal'}` создаёт сессию `kind=terminal` со статусом `shell`: обычный
  шелл без хуков, MCP и `CLAUDE.md` в папке. Resume после закрытия просто запускает новый шелл. Кнопки «+» (вкладки и проекты в
  сайдбаре) открывают меню «Claude Code / Терминал»; «+» во вкладках работает в проекте активной вкладки, там же «Новый проект…».
  Копирование/вставка в терминале: Ctrl+Shift+C / Ctrl+Shift+V (по `e.code`, работает в любой раскладке; вставка через
  `navigator.clipboard.readText`). Проверено на живом PTY (второй экземпляр, `CLAUDE_BIN=node`); с настоящим `claude` и Ctrl+C не гонялось.
- **MCP:** stateless Streamable HTTP, `reply.hijack()`, `enableJsonResponse`; личность вызывающего только из
  заголовка `X-Orch-Session`. Схемы MCP-инструментов Claude подгружает лениво через ToolSearch, поэтому системный промпт про это напоминает.
- **Фоновые ошибки не должны валить процесс:** падение сервера убивает все PTY. Фоновые промисы
  (`drain`, очередь) ловят ошибки сами, плюс `unhandledRejection` только логируется.

- **Имя сессии и история:** `claude` после первого ответа сам переименовывает окно (OSC 0: `✳ Greeting exchange`, до этого заглушка
  `Claude Code`). `LiveSession` вырезает глиф (`conversationTitle` в `sessions/title.ts`), менеджер пишет имя в `sessions.title`.
  `sessions.prompted_at` ставится по хуку `UserPromptSubmit`; сессия без него (никто ничего не писал) в истории сайдбара не показывается,
  только открыта вкладкой. Архив проектов/сессий, порядок и ширина панели хранятся в `localStorage` (`orch.project`, `orch.layout`), не в БД.

## Сверка статуса по заголовку окна (`sessions/title.ts`, `reconciler.ts`)
Хуки не видят две вещи: прерывание по Esc (`Stop` не приходит) и ответ на запрос разрешения (после `PermissionRequest`
тишина до `PostToolUse`). `claude` ставит заголовок окна (OSC 0): `✳ …` = ждёт ввода, `◐`/`◑` = работает. `TitleReconciler`
(раз в секунду) правит устаревший статус и пишет событие `OrchReconcile` в `events` для аудита:
- `waiting → busy`, если спиннер появился *после* входа в `waiting` и держится ≥0.8 с;
- `busy → idle`, если после входа в `busy` был виден спиннер, затем `✳` ≥5 с и ≥5 с без хуков, субагентов нет.
Консервативно по умолчанию: ложный `idle` опаснее зависшего `busy` (двойная доставка сообщения). Проверено на живом
`claude`: после выдачи разрешения `busy` через ~1.4 с, после Esc `idle` через ~5.6 с и следующее сообщение доставилось;
при нормальных сценариях поправок 0. Если заголовок изменится в новой версии, сверка просто молчит (хуки остаются основными).

## Известные проблемы и идеи (по приоритету)
1. ~~Зависший статус после Esc и выдачи разрешения~~ **исправлено** сверкой по заголовку окна (раздел ниже). Остаётся
   непокрытым: Esc прямо на диалоге разрешения (заголовок и там `✳`, отличить от ожидания нельзя, останется `waiting`),
   и терминалы, где спиннер заголовка другой (распознаются `◐◑◒◓` и брайль U+2800–28FF; остальные глифы игнорируются).
2. ~~Возобновление через `claude --resume`~~ **сделано**: `session_id` из SessionStart хранится в `sessions.claude_session_id`,
   `POST /api/sessions/:id/resume` (`SessionManager.resume`) поднимает закрытую/мёртвую сессию в той же строке БД и том же
   терминале (`--resume <id>`, остальные флаги те же). Клик по сессии в сайдбаре/вкладке сам вызывает resume
   (`hooks/use-open-session.ts`). Грабли: Claude не пишет транскрипт, пока не отправлено первое сообщение, а `--resume`
   на такой сессии печатает «No conversation found» и выходит; поэтому, если разговора нет (`prompted_at` пуст, нет id или
   нет файла `transcript_path` из SessionStart), resume запускает чистый `claude` без `--resume` в той же строке и вкладке:
   после перезапуска приложения пустая сессия возвращается пустой, как у Orca (процессы мы не сохраняем, PTY умирают
   вместе с сервером). Воркер при resume становится `orchestrator` (иначе `handleSessionIdle` закрыл бы его снова, он бы
   занимал слот воркера). Старые сессии без колонки восстанавливаются по событию SessionStart в `events`.
3. Учёт токенов/ходов/длительности на задачу не реализован (в плане: брать из транскрипта).
4. Запросы разрешений у воркеров: сейчас воркер ждёт в `waiting` и человек отвечает в терминале; кнопок в UI нет.
5. Worktree и ветки `orch/*` не чистятся; название проекта не выбрано.

## Эксплуатация и тесты
- `pnpm dev` (tsx watch) **перезапускает сервер при каждой правке** в `packages/server` и убивает живые сессии.
  Для спокойной работы: `pnpm build` и `pnpm --filter @orch/server start`.
- Миграции создаёт `pnpm db:generate` (не править SQL руками), применяются при старте. Менять схему вместе с миграцией
  одним шагом, иначе перезапуск на полпути упадёт на несуществующей колонке.
- pnpm 12 игнорирует `onlyBuiltDependencies`; build-скрипты разрешены через `allowBuilds` в `pnpm-workspace.yaml`.
- Тесты (`pnpm test`, vitest): машина статусов, очередь, лимиты, задачи/уведомления, watchdog, сборка аргументов `claude`.
  Поведение с настоящим `claude` проверялось только запусками. Для таких проверок поднимайте **второй экземпляр**
  (`PORT=4195 DATA_DIR=./data/test`), чтобы не убивать рабочие сессии. Порты вроде 4190 запрещены в `fetch` (ManageSieve).
- Проверено запусками: сессии/терминал/буфер, хуки и статусы, очередь, MCP `create_task`/`report_result`, worktree,
  уведомление создателя, запрет `Agent`, watchdog при убийстве процесса, сверка по заголовку (Esc и выдача разрешения), WebSocket Origin/токен, `pnpm dev`, собранный `dist`.
  Не проверялось: Linux/macOS, `suspicious` на живой сессии (только юнит), `PreCompact`, фоновые задачи после `Stop`.

## Десктоп-оболочка (`packages/desktop`)
Electron только показывает окно с `http://127.0.0.1:<PORT>/` и даёт одну функцию `window.orch.pickFolder()` (preload,
`contextIsolation`, `sandbox`; диалог открывается только для страницы с origin сервера). Сервер Electron не импортирует и
запускается системным `node` (`node-pty`/`better-sqlite3` собраны под Node ABI, не под Electron). Остановка: сообщение
`shutdown` по IPC-каналу (на Windows сигналы не дают корректного выхода); если сервер уже был запущен до окна, окно его не гасит.
Проверено: запуск на втором экземпляре (`PORT=4195`), мост в странице, `require`/`process` недоступны, закрытие окна гасит
сервер. Postinstall Electron под pnpm 12 может не скачать бинарник: `node packages/desktop/node_modules/electron/install.js`.
Не проверялось: сам системный диалог (нужен клик человека), macOS/Linux.
`pnpm app:dev` (`packages/desktop/scripts/dev.mjs`) это супервизор для разработки: Vite с HMR (окно получает
`ORCH_DEV_URL`, сервер не трогает, профиль `userData-dev`), esbuild watch сервера (опции импортируются из
`server/scripts/build.mjs`) с перезапуском по IPC `shutdown` и watch main/preload с перезапуском Electron. Отдельный
экземпляр: 4185/5183, `data/dev`. Проверено: правка сервера даёт штатный перезапуск, ошибка сборки оставляет старую версию,
правка main перезапускает окно, HMR, закрытие окна гасит сервер и Vite.
